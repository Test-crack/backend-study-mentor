1.  Purpose &amp; context
The Diagnostic Engine is the entry gate for every new student on TestCrack. Before a student can access any practice module, the system must establish a baseline band score across all four IELTS skills. This baseline drives everything downstream: the level assignment (A/B/C), the content that is unlocked, and the first batch of suggestions generated by the recommendation engine.

Without a completed diagnostic, the student sees a locked dashboard. The diagnostic cannot be skipped. This document describes exactly how the engine works, how the frontend must render and respond to each state.
Why this matters to the product
The diagnostic is the first impression. A student who completes the 10-minute gate and immediately sees their band scores, their level badge, and three targeted suggestions will trust the platform. A student who lands on a blank dashboard with no context will leave. Get this right before anything else.

4.  Screen states Frontend must handle
Every screen in the diagnostic flow has multiple states. Frontend must implement all of them â€” missing a state causes blank screens or frozen UIs that break user trust.

4.1  DiagnosticGateScreen
idle â€” student has not yet started. Show CTA, estimated time (10 minutes), and brief description of what the test covers.
in_progress â€” student already started but closed the app. Show 'Resume diagnostic' CTA with the phase they were on.
complete â€” diagnostic already done. Redirect to Dashboard immediately. Do not show the gate again.

4.2  DiagnosticScreen  (per skill section)
loading â€” API call to fetch questions is in flight. Show skeleton loader, never a blank screen.
ready â€” questions loaded. Enable interaction. Timer starts (if applicable).
submitting â€” student has submitted. Disable all inputs. Show loading indicator on submit button.
scoring â€” backend is scoring. Show spinner with contextual message (differs for AI vs. rule-based scoring).
scored â€” result received. Show interim result card before moving to next section.
error â€” API call failed. Show error message with retry option. Do not lose student's answers â€” keep them in local state.

4.3  RecordButton  (Speaking)
idle â€” ready to record. Tap to start.
recording â€” waveform animation playing. Timer counting up. 'Tap to stop' label.
recorded â€” recording stopped. Audio playback control available (optional at MVP). 'Submit' CTA enabled.
uploading â€” file uploading to backend. Spinner. Prevent double-tap.
processing â€” Whisper + Claude pipeline running. 'Transcribing...' message.
done â€” scores returned. Transition to SpeakingResultCard.

4.4  DiagnosticSummaryScreen
pending â€” not all 4 skills scored yet. Should not be reachable, but show a safe loading state if hit.
ready â€” all scores present. Show band cards for all 4 skills, level badge, and 'Go to dashboard' CTA.


5.  API contract  (what Frontend calls &amp; expects)
These are the endpoints Frontend calls. Sarthak will implement them. Both must agree on request/response shapes before either starts building. Confirm these shapes together before sprint start.

GET /api/diagnostic/status/:studentId
Returns the current diagnostic completion state.

Response field
listening_scored, reading_scored, writing_scored, speaking_scored (each boolean), overall_complete (boolean)
Use case
Polling or realtime subscription to determine when to advance the flow
Polling interval
Every 2 seconds max. Stop polling once overall_complete = true

POST /api/diagnostic/submit-section
Submits answers for Listening or Reading.

Request body
{ student_id, skill: &quot;listening&quot;|&quot;reading&quot;, answers: { q1: &quot;A&quot;, q2: &quot;TRUE&quot;, ... } }
Success response
{ ok: true, band_score: 5.5, level: &quot;B&quot; }
Error response
{ ok: false, error: &quot;string&quot; }

POST /api/diagnostic/submit-writing
Submits the writing paragraph response for AI scoring.

Request body
{ student_id, text: &quot;The graph shows...&quot; }
Success response
{ ok: true, band_score: 6.0, sub_scores: { task: 6.0, coherence: 6.5, lexical: 5.5, grammar: 6.0 }, feedback: &quot;Your task response is clear but...&quot; }
Timeout
Set client-side timeout to 20 seconds minimum

POST /api/diagnostic/submit-speaking
Submits the audio recording as a multipart/form-data upload.

Request body
FormData: { student_id, audio: File (webm or mp4) }
Success response
{ ok: true, band_score: 5.5, sub_scores: { fluency: 5.5, lexical: 6.0, grammar: 5.0, pronunciation: 5.5 }, transcript: &quot;Well, I think that...&quot; }
Timeout
Set client-side timeout to 30 seconds minimum â€” Whisper + Claude adds latency

Supabase realtime vs polling â€” if Supabase realtime subscriptions are not yet set up, use the polling approach (GET /api/diagnostic/status every 2 seconds). Confirm with Sarthak which approach the backend supports.
